# Ревью следующего diff: доставка задач и прерванная обработка

## Граница
Отдельное дополнение к предыдущему selfservice-кандидату. Не применено к рабочему репозиторию пользователя, БД или серверу. Docker/Django/PostgreSQL/Redis/Celery здесь не запускались и не устанавливались. Производственная надёжность не подтверждена.

Это не CRM для операторов и не новая очередь ручного юридического согласования. Техническая диагностика требуется только при сбое сервиса. У клиента остаются услуги, заявки и результаты.

## Предлагаемые файлы и последствия

|---|---|---|

| reliability.py | Чистые правила переходов, backoff, ручного восстановления | Проверяемые unit-тестами правила, но не доказательство транзакций PostgreSQL |

| admin.py | DispatchRecord read-only | Техническому администратору видны число публикаций, времена и код ошибки, без отдельной админ-темы |
| management/commands/recover_service_request.py | По умолчанию только просмотр; восстановление с двумя явными флагами | Только synthetic non-AI failed/needs_review без опубликованного файла; до 3 попыток. Нет публичного route или автоматического восстановления |
| templates/capexly/result.html | Терминальный статус «Обработка прервана» | Прекращается бессмысленный polling, заявка не исчезает, ИИ не перезапускается автоматически |
| tests | 20 pure policy tests; 13 подготовленных PostgreSQL integration tests; усилен тест идемпотентности | Старые проверки не отключены и не ослаблены |

## Роли, порты и безопасность
- Роли PostgreSQL, GRANT/владение/секреты не меняются. Схему меняет migrator, runtime получает только прежние DML/sequence privileges через ранее подготовленный механизм. После миграции всё равно обязательно реально проверить grants.
- Company owner/member/viewer не меняются. Клиент не получает команды восстановления или доступ к outbox admin.
- Портов, образов, Compose сетей/томов и новых внешних сервисов в этом diff нет.
- Ключи ИИ не добавлены, внешний ИИ остаётся выключенным по умолчанию. Повтор заявки с use_ai=True запрещён новой recovery-командой даже если предыдущий вызов мог не дойти до провайдера.
- В журнале отправки нет текста документов или ключа. Исключения брокера/ИИ не выводятся с их телом; для диагностики логируется тип ошибки. Технические UUID не являются permission token.
- Блокировки Company → ServiceRequest перед началом и публикацией согласованы с отзывом membership. Результат проверяется на принадлежность текущему поколению обработки.
- Изоляция компаний и RLS всё ещё НЕ приняты. Read-only admin не превращает глобального staff в клиента одной компании.

## Алгоритм
1. В одной транзакции создаются заявка, outbox intent и событие submitted.
2. После commit — необязательный быстрый publish. Если процесс умер до callback, intent уже в БД; периодическая выборка должна его обнаружить.
3. Broker failure сохраняет queued и планирует новый publish с backoff 5…300 секунд. Это повтор доставки сообщения, НЕ повтор уже начатого ИИ-вызова.
4. После принятия сообщения broker'ом queued не считается успешным документом. Если сообщение потерялось и заявка ещё queued, публикация возможна снова через 60 секунд. Пока broker недоступен, beat тоже не сможет доставить maintenance задачи; при восстановлении нужен живой beat/worker. Сама БД от этого не становится независимым планировщиком.
5. Worker под блокировкой заявляет generation token и processing. Повторное сообщение для processing/ready не запускает обработку.
6. Запись готового результата допускается только если generation token всё ещё актуален и состояние processing. Старый worker после fencing не может перезаписать новую попытку. Опубликованный файл не удаляется при неоднозначном результате DB commit: возможный orphan сохраняется для диагностики.
7. Более 15 минут processing (или старый processing без timestamp) → needs_review, без auto-replay. 15 минут — критерий технического вмешательства для этого пилота, не юридический срок и не обещание SLA.
8. Оператор может отдельно подтвердить повтор только детерминированной заявки без ИИ. Старая generation снимается; возможный поздний worker не получает права публикации. Опубликованные файлы не удаляются и не заменяются recovery-командой.

## Что НЕ гарантируется
- Проверки гонок и транзакций с настоящим PostgreSQL ещё не выполнены. Python decision tests не доказывают select_for_update/skip_locked или работу Redis.
- Отправка в провайдер и подтверждение оплаты не образуют транзакцию с БД. Для внешнего ИИ crash/timeout означает неизвестный исход, а не гарантию отсутствия расхода. Exactly-once и «невозможность повторного списания» не заявляются.
- Нет heartbeat активного provider call; очень медленная обработка может быть fenced как прерванная. Для ИИ это безопаснее автоматического повтора, но требует ручной сверки.
- Нет автоматического удаления orphan-файлов после kill. Файл с неопределённым commit сохраняется, не удаляется вслепую. Нужен будущий отдельный реестр/сверка orphan при реальном S3.
- Наличие maintenance-задач не заменяет мониторинг/оповещение о dead beat, dead worker, очереди и состоянии БД.
- Старые worker v1 не знают generation fencing. Одновременный запуск v1/v2 не поддержан: нужен согласованный coordinated rollout всех web/worker/beat без смешивания версий.
- Старые инфраструктурные блокеры (stale uv.lock, prod-test Garage 0444, незапущенные image/restore/transfer/VPS/S3 tests) этим diff не исправлены.

Статический экран нового needs_review отрисован и просмотрен на 1440/390px. git apply --check/byte comparison проверяются отдельно при упаковке. Подготовленные 13 новых integration tests не выполнялись; вместе с прежними 10 selfservice access tests это 23 непроверенных integration tests, не «23 успешных проверки».
