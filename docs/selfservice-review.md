# Пакет ревью: кабинет и синтетический S-03

## Статус
Это отдельный кандидат, а не изменения вашего работающего репозитория. В окружении агента нет Docker и Django. Полный путь «регистрация → заявка → worker → приватный S3 → скачивание» НЕ проверен. Реальные документы запрещены. Приложение здесь не объявляется готовым к production.

Основа бесплатного стартера: saaspegasus/django-boilerplate, commit e9d11b0a294191af87fec6f84acb4d96454957be. Кандидат предполагает ранее подготовленный инфраструктурный пакет и каталог service_catalog. Состояние вашего локального Git не предоставлено: автоматического перезаписывания нет.

## Что предлагается согласовать одним пакетом
- apps/selfservice/: Company, Membership, ServiceRequest, RequestEvent; явная миграция 0001_initial. Новые таблицы, без изменений ролей PostgreSQL и без RLS. Миграции только отдельным migrator.
- Роли кабинета: owner управляет доступами и создаёт заявки; member создаёт и видит результаты; viewer видит результаты. Все три роли видят общие результаты своей компании. Это НЕ роли PostgreSQL. Технический staff в Django Admin — доверенный глобальный оператор, не клиент компании; выдавать staff клиентам нельзя.
- Доступы: владелец добавляет только существующую зарегистрированную учётную запись. Без рассылки приглашений, подтверждения приглашения и самостоятельной смены владельца на этом этапе. Общения и задач нет.
- Новые URL: /cabinet/, /cabinet/start/, /cabinet/services/payment-claim/, /cabinet/requests/<uuid>/, status/, download/, /cabinet/access/. Изменения данных — POST + CSRF. company не берётся из формы заявки.
- project/settings.py: подключение app, возврат после штатного входа в /cabinet/, выключенный по умолчанию пилот/ИИ. Allauth не заменяется. Унаследованные формы входа/сброса пароля используют новый внешний layout, а не новую авторизацию.
- templates/capexly и static/capexly: самостоятельные Django templates и CSS/JS в существующей сборке, без React/Next.js/CDN и отдельного frontend-приложения. Штатная daisyUI не удалена, Django Admin не переоформляется.
- compose.pilot.dev.yaml: ТОЛЬКО дополнительный opt-in overlay для синтетического dev. Передаёт одинаковый флаг web/worker/migrate; внешнее ИИ выключено. Порты, сети, тома, секреты и команды deployment этот overlay НЕ меняет. Не добавлять в prod.
- Порты остаются прежними: localhost:8000 web, :5173 frontend-dev, :3900 Garage, :8025 Mailpit. Никакой новой публикации портов. Production Caddy 80/443 не меняется этим патчем.
- Результат сохраняется отдельным worker через существующий default_storage, отдаётся через проверяющий компанию Django download. URL файла не показывается. HTML/JSON/download защищены no-store. Доступ из браузера проверяется заново при запросе; это не доказанная tenant isolation.
- Из 57 каталожных записей обработчик есть только у S-03. Flags скрыты по умолчанию. Явная команда активирует только S-03 в синтетическом dev.

## ИИ
Рабочая функция по умолчанию — детерминированный шаблонный черновик, НЕ проверенный ИИ-юрист. Отключённый адаптер Zen принимает только синтетический текст; требует явную совместимую модель и runtime secret-файл, не делает retries и не заменяет факты/сумму в DOCX. Ответ показывается отдельно как непроверенная подсказка. GigaChat/YandexGPT не подключены. Реальный provider call не выполнялся.

Ранее опубликованный в чате ключ нужно отозвать и заменить. Он не использован и не включён в файлы. Новый ключ передавать через secret, не чат, Git, build args или логи. Нельзя просто отправить реальные клиентские данные в Zen. Нужны отдельное решение по провайдеру, размещению и правовым основаниям обработки. Формат API зависит от модели: https://opencode.ai/docs/zen/ .

## Стоп-факторы
1. У старого инфраструктурного кандидата uv.lock не синхронизирован: сборку нельзя объявлять успешной. Нужен controlled uv lock в tooling-контейнере, просмотр diff, uv lock --check, затем сборка.
2. Docker/Django/Postgres отсутствуют здесь. 10 интеграционных тестов доступа, идемпотентности, шаблона и CSRF только написаны, не выполнены. Нужен тест под runtime ролью и миграции под migrator. Проверка миграции makemigrations --check --dry-run тоже не выполнена.
3. Политик RLS нет. Нужен отдельный аудит доступа и legacy endpoints стартера, включая admin/API/celery-progress/media, перед реальными данными.
4. Worker crash в processing может оставить заявку зависшей. Нет надёжного outbox и автоматического безопасного восстановления; нужен контролируемый recovery с учётом возможного внешнего ИИ-расхода. Не сбрасывать state молча и не переотправлять платный запрос вслепую.
5. Приватный S3, живой worker, вход/письма, backup/restore, перенос image archive и CI не запускались. VPS, публичный HTTPS и российский S3 не предоставлены.
6. В старом prod-test Garage Compose secret может оставаться 0444. Dev-исключение не переносится в prod-test/prod. Там отдельно подготовить 0600 и проверить UID/GID/entrypoint; здесь это не исправлено.
7. Нельзя считать полный пункт «одна услуга полностью работает» закрытым по кликабельному HTML.

## Что исправлено по ходу ревью
Отсутствующий символ логотипа заменён SVG; разделены состояния шапки гостя/кабинета; выделен активный раздел; увеличена область checkbox-label; усилены границы полей; обработан невалидный UUID; повторный idempotency key проверяется до квоты; onboarding сериализован блокировкой пользователя; cleanup не маскирует ошибку задачи; запрещены HTTP-редиректы с bearer; результаты закрыты от кеширования. Для исправлений серверной части подтверждён только код, не конкурентный PostgreSQL runtime.
