# Подключение следующих услуг

Не создавайте по приложению с новой авторизацией для каждой услуги. Общие части: Company/Membership, вход allauth, каталог, заявки, очередь, приватный storage и результаты. Специфичны только форма, валидация, обработчик и формат результата.

1. Выбрать запись исходного каталога и уточнить её класс: клиентская услуга, пакет, функция платформы или коммерческая гипотеза. Не все 57 записей являются самостоятельными услугами.
2. Зафиксировать service-code, входную схему, обязательные подтверждения и версию движка. Описать чего сервис не подтверждает, правила проверки, запреты и критерии приёмки.
3. Добавить явный обработчик в registry доверенного кода, не импортировать Python пути из БД. Пока can_be_requested дополнительно требует flags и handler.
4. Добавить форму/route/worker handler и тесты. Текущий ServiceRequest код пока технически обслуживает ТОЛЬКО S-03. Само добавление registry-записи недостаточно: dispatch, UI и схема результата должны стать общими при второй услуге; сейчас намеренно не строится универсальный движок.
5. Версионировать входную схему и шаблон, не менять смысл старых результатов при обновлении. Хранить реквизиты отдельно от опционального LLM-текста; не доверять ответу LLM как сумме, факту или правовой норме.
6. Проверить чужую компанию/IDOR, viewer POST, revoked membership, CSRF, idempotency, гонки, блокировку по роли, ошибки очереди, файлы, квоты, запрет внешней сети по умолчанию. Запускать под ограниченной ролью PostgreSQL. RLS/доказанная tenant isolation — отдельный обязательный допуск перед реальными данными.
7. Для ИИ: отдельный adapter, разрешённый endpoint, формат конкретной модели, runtime secret, timeout/лимиты, privacy/cost review. GigaChat/YandexGPT имеют свою авторизацию и контракты: нельзя переименовать endpoint Zen и считать интеграцию готовой.
8. Обновить документацию и activation gate. Seed не перезаписывает административные правки и не включает услугу. Не публиковать даты, тарифы, гарантии и кнопки неработающей услуги.
9. После integration tests и ревью — явная активация в согласованном окружении. Отдельно подтвердить возможность real data; наличие working handler не даёт этого разрешения.

Текущая политика: все участники компании читают общие результаты; viewer не создаёт; member создаёт; owner управляет доступами. Для приватных личных результатов внутри компании нужна новая спецификация и тесты, сейчас такого режима нет.
